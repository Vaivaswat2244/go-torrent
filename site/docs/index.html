Install

go-torrent builds from source with the Go toolchain (Go 1.21 or later):

go install github.com/Vaivaswat2244/go-torrent/cmd/client@latest

That installs a binary named client into your GOBIN. To build it under its own name, clone the repository and run:

go build -o go-torrent ./cmd/client

Usage

go-torrent [-output <dir>]

The client opens a menu where you choose a .torrent file or paste a magnet link. For magnet links, metadata is fetched from peers first, which can take up to a minute.

Keys: ↑/↓ and enter to navigate, esc to go back or cancel a metadata fetch, q or ctrl+c to quit.

When a download finishes the client keeps running and seeds until you quit or a ratio or time limit is reached.

Options

flagwhat it does
-outputOutput directory. Default: the current directory.
-portTCP port to listen on for incoming peers. Default: 6881.
-max-peersMaximum simultaneous peer connections. Default: 50.
-seed-ratioStop seeding at this upload/download ratio. 0 means unlimited.
-seed-timeStop seeding after this long, e.g. 2h. 0 means unlimited.
-encryptionprefer, require, or off. Default: prefer.

Seeding and reachability

Peer connections are bidirectional, so the client uploads both to peers that connect to it and to peers it connects to. Unchoking follows the standard choke algorithm: four unchoke slots recomputed every 10 seconds, ranked by reciprocation while downloading and by upload rate while seeding, plus an optimistic unchoke every 30 seconds.

There is no UPnP or NAT-PMP, so if you are behind NAT, peers cannot open connections to you unless you forward the port yourself:

go-torrent -port 6881

Forward TCP port 6881 (or whichever port you chose) on your router to the machine running go-torrent. Without a forwarded port you will still upload on connections you initiate, just to fewer peers.

Encryption

Some networks, campuses and workplaces especially, reset any connection that looks like BitTorrent. They spot it from the first bytes of a plain connection, which are always the same.

go-torrent supports Message Stream Encryption (MSE, also called protocol encryption), the obfuscated handshake mainstream clients use. It is on by default: connections are encrypted where the peer supports it, which nearly all do, and fall back to plain BitTorrent otherwise. This covers magnet metadata fetches too, which otherwise fail on filtering networks before a download can start.

go-torrent -encryption prefer    # default: encrypt, fall back if needed
go-torrent -encryption require   # never use a plain connection
go-torrent -encryption off       # plain BitTorrent only

If downloads work elsewhere but not on a particular network, try require.

MSE hides BitTorrent from filters; it is not privacy. The key exchange is unauthenticated, and your IP address is visible to every peer and tracker as usual. Note also that MSE only applies to peer connections: the DHT and UDP trackers are not covered. A network that blocks those will still limit peer discovery; trackers over HTTPS are unaffected.

Resume

If the output directory already contains data for the torrent, it is re-hashed on start and valid pieces are skipped, so an interrupted download continues where it left off. Verification runs off the UI thread, so the interface stays responsive while existing data is checked.

Troubleshooting

The download shows a stall message. The message says why: no peers, nobody has the remaining pieces, or how many remaining pieces are queued and how many are held by peers. A stall with connected peers usually resolves itself; pieces held by an unresponsive peer are reassigned after 30 seconds without data.

Downloads work at home but not on this network. The network is probably filtering BitTorrent. Run with -encryption require. If the torrent relies on UDP trackers or DHT for peers, discovery may still be limited, since MSE covers only peer connections; magnet links and torrents with HTTPS trackers fare best.

To check whether a network is blocking BitTorrent, compare plain and encrypted handshakes against real peers:

GOTORRENT_LIVE=1 go test ./internal/engine/ -run TestLiveHandshakes -v

If plain handshakes succeed for nobody but encrypted ones do, the network is filtering BitTorrent and require is the setting to use.

Few or no peers upload to me. If you are behind NAT without a forwarded port, peers cannot connect to you; see seeding and reachability.

Not implemented

UPnP/NAT-PMP port mapping, DHT announce_peer (so DHT users cannot discover you; trackers can), PEX, rarest-first and endgame piece selection, superseeding, the fast extension, rate limiting, multiple simultaneous torrents, IPv6, and base32 magnet links.

Development

go build ./...
go vet ./...
go test -race ./...

The race detector matters here: the piece bitfield is shared between the download loop and every peer goroutine. Network tests are skipped unless you opt in:

GOTORRENT_LIVE=1 go test -race ./internal/engine/ -v -timeout 10m

The seeding tests need no network — they run a seeder and a leecher against each other over loopback, under every combination of encryption settings.

Changes per release are in the release notes.
